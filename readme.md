> **The failure OpenDomain catches:** an AI coding assistant produces syntactically complete, internally consistent, test-passing software whose **domain semantics were invented rather than known**. That is not a modelling error — it is an *epistemic* one. The assistant cannot distinguish a reconstructed domain rule from a plausible hallucination, because nothing records what is known, assumed, inferred, or unknown.
>
> **OpenDomain stores that distinction explicitly and enforces it mechanically** — twice over: at rest, on the linked artifacts of the workspace; at runtime, on every output an execution agent produces before that output reaches its consumers.

## What it gives you

| Capability | How |
|---|---|
| **Epistemic honesty** | Every artifact carries `EXPLICIT` · `TACIT` · `HYBRID` · `INFERRED` · `ASSUMED` · `UNKNOWN` · `CONFLICTING` |
| **Traceability spine** | One ordered chain: source → evidence → domain → requirement → spec → plan → code → test → validation |
| **Two mechanical answers** | `opendomain trace REQ-012` — *why does this exist?* · `opendomain impact RULE-007` — *what breaks if this changes?* |
| **9 deterministic gates** | 63 named rules (`gate-3/unjustified-requirement`, …). Pure functions: no mutation, stable slugs, exact citations |
| **Verified execution** | A DAG of agents runs under the same discipline: every output passes its rejection gate (`yᵢ ∈ Cᵢ`) before it propagates — *Generate → Verify → Attribute → Refine* |
| **Agent-native** | `AGENTS.md`, 15 slash-commands, 3 role agents, 7 skills - generated by `opendomain init` for any coding agent |

> The agent-executed flow, end to end — the six phases, the run archive, the typed attributions — is documented in [The harness](https://gayensis09.github.io/OpenDomain/docs/harness.html).

```bash
opendomain trace REQ-012          # why does this exist?
opendomain impact RULE-007        # if this changes, what breaks?
```

## Install

Requires **Rust 1.75+**. No clone needed — `cargo install` puts `opendomain` in `~/.cargo/bin`, already on your `PATH`:

```bash
cargo install opendomain-cli                                            # from crates.io
cargo install --git https://github.com/GAYENSIS09/OpenDomain --locked opendomain-cli   # from this repository
opendomain --version
```

Alternative from a checkout:

```bash
git clone https://github.com/GAYENSIS09/OpenDomain
cd OpenDomain
cargo install --path crates/opendomain-cli --locked
```

## Start here

```bash
mkdir my-project && cd my-project
opendomain init --name my-project
opendomain status
```

`opendomain init` **installs only** — registries + `opendomain.toml` + the agent contract. It records no context: run `/opendomain-project` afterwards to fill `project.md`, `[project]`, `DOM-001`/`STK-001` from the repository, external research, then user answers. Each generated tree carries its own `.gitignore` — regenerable like the rest of the scaffold, and the project's own `.gitignore` is never touched: a project that versions a tree (the registries are the cited F14/L9 evidence) deletes that tree's `.gitignore`. Inside a git repository it advises the split (the registries are the cited evidence, `opendomain provenance` verifies the citations).

Beyond the `opendomain/` directory of **42 files** — 34 registry files (one per artifact kind, from `SRC` to `TEST`), six explanatory files (`README.md`, `project.md`, the research protocol, the architecture overview, the specs and changes READMEs), `opendomain.toml` and the tree's own `.gitignore` — it writes the **agent contract** at the project root, so the framework is usable by any coding agent rather than only by someone who has read the paper: `AGENTS.md` plus the `.opencode/` tree (15 commands, 3 role agents, 7 skills, and the tree's own `.gitignore`). **In total, `opendomain init` writes 69 files.** It is idempotent — re-running it reports what already exists and changes nothing.

```
AGENTS.md                          # the rules, readable by any agent
.opencode/command/                 # /opendomain-status, /opendomain-gate, /opendomain-trace, /opendomain-impact,
                                   # /opendomain-audit, /opendomain-record, /opendomain-project, /opendomain-research,
                                   # /opendomain-domain, /opendomain-requirements, /opendomain-opportunity,
                                   # /opendomain-spec, /opendomain-plan, /opendomain-harness, /opendomain-complete
.opencode/agent/                   # context-completer, domain-researcher, opendomain-harness
.opencode/skills/                  # opendomain, -artifacts, -epistemics, -research, -gates, -harness, context-completer
```

`AGENTS.md` is never overwritten, not even with `--force`: if you already keep your own, `opendomain` does not claim it. The namespaced `.opencode/` files are written by `opendomain` and are refreshed by `--force`.

```bash
opendomain init --profile lean # start at Stage 3; the domain model exists elsewhere
opendomain init --profile core # stages 0, 1, 3-8 (no opportunity discovery)
opendomain init --profile full # everything (default)
opendomain init --dry-run # report what would happen, write nothing
```

Other init flags: `--repository greenfield|brownfield|hybrid` and `--authority spec-first|spec-anchored|spec-as-source`.

> **New to OpenDomain?** Start with the [documentation](https://gayensis09.github.io/OpenDomain/) — [5-minute guide](https://gayensis09.github.io/OpenDomain/docs/getting-started.html) → [core concepts](https://gayensis09.github.io/OpenDomain/docs/concepts.html) → [the 9 gates](https://gayensis09.github.io/OpenDomain/docs/gates.html).

## Working with `opendomain`

`opendomain` **reads and checks**; it does not author. You write the artifacts, `opendomain` tells you whether they are consistent.

```bash
opendomain status                        # where does the project actually stand?
opendomain gate context                  # what is missing before the domain can start?
opendomain gate --through 2               # run every gate up to the domain stage (0-8)

opendomain link --check                  # every referenced id must exist
opendomain link REQ-012 derived-from EVD-014   # declare an edge (writes the TOML block)
opendomain advance REQ-012 VALIDATED     # move along the lifecycle
opendomain show REQ-012                  # one artifact's full record

opendomain trace REQ-012                 # why does this exist?
opendomain trace --forward REQ-012       # what implements and verifies it?
opendomain impact RULE-007               # what breaks if this changes?
opendomain graph --root REQ-012 --depth 3
opendomain audit                         # traceability health across the workspace
opendomain reference                     # the gates and the 37 artifact kinds
```

The verification subsystem (Sections 9/10 of the paper — the rigour table, the
generated executable specifications, the binding-provenance record, the
provisioner, in that order, each gated on the previous):

```bash
opendomain rigour                        # the §9.7 rigour table + workspace audit
opendomain provision --dry-run           # stack detection + ordered selection, nothing written
opendomain provision                     # generated .feature scaffolds (@AC tags, provenance) — or a recorded refusal
opendomain bind                          # binding provenance + verification depth audit (findings, not gate rules)
opendomain provenance                    # verifies each run citation against the archived run it names (F14)
```

Change proposals follow the OpenSpec layout:

```bash
opendomain propose tighten-reservation --summary "Tighten the reservation window"
opendomain apply tighten-reservation
opendomain archive tighten-reservation
```

### The nine gates

```
0         1          2        3              4             5               6      7                8
context → research → domain → requirements → opportunity → specification → plan → implementation → completion
```

Cumulative: passing gate 8 means gates 0–7 passed too.

| Gate | Question it asks |
| ---- | ---------------- |
| `context` | Do we know what we are building, and what is already true? |
| `research` | Is the domain understood well enough to derive requirements? |
| `domain` | Is the domain model coherent, owned and cross-linked? |
| `requirements` | Is every requirement justified, testable and traced? |
| `opportunity` | Has anything been challenged, and is the chosen concept earned? |
| `specification` | Does the specification describe observable behaviour and nothing else? |
| `plan` | Is there a bounded, ordered plan that can realise the specification? |
| `implementation` | Did implementation satisfy the acceptance criteria without drift? |
| `completion` | Is the whole chain coherent, tested and free of critical unknowns? |

`opendomain reference` prints this list as a rendered report; `opendomain reference --json` returns it machine-readably, grouped by gate, with each rule's severity.

Findings carry one of two severities. `Blocking` fails the command — `opendomain` exits non-zero — and means the phase cannot be considered complete. `Advisory` is reported and does not fail the command. The paper specifies three levels (`BLOCKER`, `WARNING`, `NOTE`); the implementation has two, and the paper's Section 11.7 records the six conditions whose severity disagrees with its own specification.

Gates are pure functions from the workspace to a report: they never mutate state, so running one twice gives the same answer, and a failure names the exact condition that broke.

### Scripts and CI

`--json` works on every command that reports. A failing gate exits non-zero, so `opendomain gate --through 5` works as a CI step.

```bash
opendomain gate --through 5 --json > gate-report.json
```

`--no-color` and `-C <dir>` are available everywhere. `--strict` is accepted for explicitness and currently changes nothing: blocking findings always fail the command and advisory ones never do. `advisory_gates` in `opendomain.toml` and the `[schemas]` section are likewise written by `opendomain init` but not read by the CLI today.

## Using it with opencode

This repository ships a working opencode integration. If you point opencode at a project that has an `opendomain/` workspace, the following become available automatically.

**Slash commands**

| Command | What it does |
| ------- | ------------ |
| `/opendomain-status` | Where the project stands, and what is blocking |
| `/opendomain-gate <gate>` | Runs a gate and reports the findings verbatim |
| `/opendomain-trace <ID>` | Explains why an artifact exists, from its recorded links |
| `/opendomain-impact <ID>` | What a change to an artifact would break |
| `/opendomain-audit` | Traceability health before claiming work is done |
| `/opendomain-record <topic>` | Writes a domain artifact, keeping its epistemic state honest |
| `/opendomain-project` | Completes Phase 0 context (repo scan + external research + user questions) |
| `/opendomain-research` | Gate 1 research, parallel keyword fan-out via `domain-researcher` |
| `/opendomain-domain` | Gate 2 domain model increment |
| `/opendomain-requirements` | Gate 3 justified, testable requirements |
| `/opendomain-opportunity` | Gate 4 challenged concept + falsifiable hypothesis |
| `/opendomain-spec` | Gate 5 observable-behaviour spec + acceptance criteria |
| `/opendomain-plan` | Gate 6 bounded, ordered plan |
| `/opendomain-complete` | Gate 8 full alignment audit before release |

One command per gate keeps usage simple: run the command for the stage you are in; it loads the skill, delegates to the right subagent, then shows `opendomain gate` verbatim. No extra orchestration to learn.

**Subagents** (only 3 — one role each, calling each other)

- `context-completer` — owns Phase 0 (`project.md` + `[project]` + `DOM-001`/`STK-001`). Reads the repo itself, **delegates external research to `domain-researcher`**, then asks human-only gaps. Called by `/opendomain-project`.
- `domain-researcher` — evidence specialist. Called by `context-completer`, `/opendomain-research`, `/opendomain-domain`, `/opendomain-requirements`; fans out 3-6 axes in parallel itself. Bash `deny` by default with `opendomain *` + read-only repo commands allowed.
- `opendomain-harness` — execution architect: one `TASK-###` record becomes a planned, grounded, gated, archived agent system; failures come back typed (`local`/`upstream`/`structural`). Doctrine in the skill `opendomain-harness`; called by `/opendomain-harness`, the only door into agent-executed work.

**Skills** (the framework's strength, loaded on demand by commands and agents)

| Skill | Loads when |
|---|---|
| `opendomain` (index) | Always-available summary; points to the five below |
| `opendomain-epistemics` | Choosing a value, recording a promotion, checking laundering |
| `opendomain-artifacts` | Writing/repairing any artifact (format, ids, relations) |
| `opendomain-research` | Gathering evidence (fan-out, triangulation, saturation) |
| `opendomain-gates` | Reading any gate/status/audit output (slug → action) |
| `opendomain-harness` | Driving the verified execution flow — build from a `TASK-###`, recover a run (verify/attribute/resume/repatch) |

```
commands (thin, UX) → subagents (roles, call each other) → skills (know-how)
readonly:  /opendomain-status /opendomain-gate /opendomain-trace /opendomain-impact /opendomain-audit
production:/opendomain-project /opendomain-research /opendomain-record /opendomain-domain /opendomain-requirements
           /opendomain-spec /opendomain-plan → /opendomain-complete
execution: /opendomain-harness — builds from a `TASK-`, recovers a `run-` (verify/attribute/resume/repatch)
                          ↘ calls /opendomain-audit for the diagnostic, then decides
```

Every command and agent renders **summary-first**: Verdict (1 line) → top-3 blockers (slug + 1 sentence) → one next action → verbatim appendix. No more wall-of-gates noise; fidelity kept in the appendix.

**Skill.** `.opencode/skills/opendomain/SKILL.md` loads on demand and carries the artifact format and the epistemic discipline. `AGENTS.md` holds the short version that is always in context, so the skill does not have to be.

To adopt this in your own project, run `opendomain init` - it writes `AGENTS.md` and the twenty-five `.opencode/` files (15 commands, 3 role agents, 7 skills) for you, and puts the `opendomain` binary on `PATH`. It does **not** write `opencode.json`: the permission file below is this repository's own, and copying it is your decision.

```json
{
 "$schema": "https://opencode.ai/config.json",
 "permission": {
 "bash": {
 "opendomain *": "allow",
 "opendomain init *": "ask",
 "opendomain link *": "ask",
 "opendomain advance *": "ask",
 "opendomain apply *": "ask",
 "opendomain archive *": "ask"
 }
 }
}
```

`opendomain *` is allowed and the five mutating subcommands are asked for, so reading the project is frictionless and changing it still needs consent. The `domain-researcher` subagent is stricter still: its own frontmatter denies all bash except `opendomain *`, so it can check its work and can run nothing else.

> opencode reads its configuration at startup. After adding or changing `opencode.json`, agents, commands or skills, **restart opencode** or the new definitions will not be picked up.

## The artifact format

Each registry is a Markdown file of `##` headings, one per artifact. A fenced `toml` block carries the machine-checked fields; the prose below is for humans and is never parsed.

````markdown
## REQ-012 — Consult the movement history of an item

```toml
type = "FUNCTIONAL"
status = "DRAFT"
epistemic = "INFERRED"
confidence = "MEDIUM"
actor = ["ACT-002"]
derived-from = ["EVD-014"]
rules = ["RULE-007"]
```

**Statement**

The system SHALL allow authorized users to consult the chronological movements
of an item.
````

A malformed TOML block is reported with a line number, never guessed at. The prose is free-form, so you can write as much explanation as the subject deserves without risking a parse error.

Identifiers carry their kind as a prefix — `REQ`, `EVD`, `SRC`, `RULE`, `AC`, `SPEC` and 31 others (`opendomain reference` lists them all) — optionally scoped, as in `REQ-INVENTORY-014` and `AC-INVENTORY-014-01`. Links are declared by the artifact that depends on the other, not the reverse: `REQ-004 derived-from RULE-001`.

## What gets enforced

The nine gates carry 63 named rules, each identified by a stable slug such as `gate-3/unjustified-requirement` so a failure can be cited rather than paraphrased. A representative selection:

| Rule | What it forbids |
| ---- | --------------- |
| `gate-3/unjustified-requirement` | A requirement with no `derived-from` an evidence record or business rule |
| `gate-1/orphan-evidence` | An evidence record not `derived-from` a source. An unsourced claim is not evidence |
| `gate-1/single-source` | Every evidence record citing the same single source — a claim repeated by one origin is not corroborated |
| `gate-8/assumption-reached-production` | A requirement whose `epistemic` is `ASSUMED`, `UNKNOWN` or `CONFLICTING` reaching the specification stage |
| `gate-5/how-not-what` | A specification that states mechanism rather than observable behaviour |
| `gate-4/unfalsifiable-hypothesis` | A hypothesis with no metric and no failure condition |
| `gate-4/feature-cloning` | A concept justified only by competitor parity |
| `gate-6/dependency-cycle` | Task dependencies forming a cycle |
| `gate-8/requirement-without-passing-test` | A requirement marked `IMPLEMENTED` with no verified test downstream |
| `gate-8/dangling-reference` | A link pointing at an identifier that does not exist |
| `gate-1/undeclared-epistemic` | An artifact that makes a claim but declares no epistemic state |
| `gate-7/epistemic-laundering` | An `ASSUMED` or `INFERRED` artifact marked `VALIDATED` or `VERIFIED`, with no intervening `EXPLICIT` evidence |

`opendomain audit` reports traceability health across the whole workspace, including coverage ratios, unjustified artifacts, dangling links, and open conflicts.

## Recording how a claim got stronger

An artifact's `epistemic` state is a claim about the present. A `promotions` array records how it got there:

````markdown
```toml
status = "VALIDATED"
epistemic = "EXPLICIT"
promotions = [
 { from = "ASSUMED", to = "VALIDATED", evidence = ["EVD-014"], date = "2026-04-10" }
]
```
````

Without that record, a change from `ASSUMED` to `EXPLICIT` and a change of status are indistinguishable from each other — which is precisely the edit the framework exists to catch. `gate-7/epistemic-laundering` blocks a promotion from `ASSUMED` or `INFERRED` into `VALIDATED` or `VERIFIED` that cites no evidence, cites evidence that does not exist, or cites evidence that is not itself `EXPLICIT`. It also blocks on the current state alone: an artifact that is `ASSUMED` and `VALIDATED` at once has been laundered whether or not it wrote anything down.

A workspace that records no promotions at all gets an advisory, not a blocking finding. Absence of history is not evidence that laundering happened; it is evidence that laundering is currently undetectable, which is a smaller problem and a different one.

## Repository layout

```
opendomain-core/
  ├─ crate (racine)      artifact model, parser, workspace index, graph, gates
  └─ templates/          the registries, the explanatory documents, and the
                         agent contracts (AGENTS.md, .opencode/) that
                         `opendomain init` scaffolds
opendomain-cli/          the `opendomain` binary — thin glue: the clap commands
                         that drive the engine; no knowledge of its own
docs-site/               static documentation, including the full specification
opendomain-paper.tex     the specification paper (local working copy — not committed)
opendomain.svg           the logo
AGENTS.md (generated)    agent orientation, loaded automatically by opencode
opencode.json (this repo only)  opencode configuration for this repository
```
