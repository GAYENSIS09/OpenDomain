> **The failure OpenDomain catches:** an AI coding assistant produces syntactically complete, internally consistent, test-passing software whose **domain semantics were invented rather than known**. That is not a modelling error — it is an *epistemic* one. The assistant cannot distinguish a reconstructed domain rule from a plausible hallucination, because nothing records what is known, assumed, inferred, or unknown.
>
> **OpenDomain stores that distinction explicitly and enforces it mechanically.**

## What it gives you

| Capability | How |
|---|---|
| **Epistemic honesty** | Every artifact carries `EXPLICIT` · `TACIT` · `HYBRID` · `INFERRED` · `ASSUMED` · `UNKNOWN` · `CONFLICTING` |
| **Traceability spine** | One ordered chain: source → evidence → domain → requirement → spec → plan → code → test → validation |
| **Two mechanical answers** | `od trace REQ-012` — *why does this exist?* · `od impact RULE-007` — *what breaks if this changes?* |
| **9 deterministic gates** | 58 named rules (`gate-3/unjustified-requirement`, …). Pure functions: no mutation, stable slugs, exact citations |
| **Agent-native** | `AGENTS.md`, 6 slash-commands, 2 subagents, 1 skill — generated by `od init` for any coding agent |

```bash
od trace REQ-012          # why does this exist?
od impact RULE-007        # if this changes, what breaks?
```

## Install

Requires **Rust 1.75+**. No clone needed — `cargo install` puts `od` in `~/.cargo/bin`, already on your `PATH`:

```bash
cargo install --git https://github.com/GAYENSIS09/OpenDomain --locked opendomain-cli
od --version
```

Alternative from a checkout:

```bash
git clone https://github.com/GAYENSIS09/OpenDomain
cd OpenDomain
cargo install --path crates/opendomain-cli --locked
```

## Start here

```bash
mkdir my-project && cd my-project
od init --name my-project
od status
```

`od init` creates an `opendomain/` directory of **41 files**: 33 registry files, seven explanatory files (`README.md`, `project.md`, the research protocol, the architecture overview, the specs and changes READMEs, the validation audit) and `opendomain.toml`. It is idempotent — re-running it reports what already exists and changes nothing.

It also writes an **agent contract** to the project root, so the framework is usable by any coding agent rather than only by someone who has read the paper:

```
AGENTS.md                          # the rules, readable by any agent
.opencode/command/                 # /od-status, /od-gate, /od-trace, /od-impact,
                                   # /od-audit, /od-record
.opencode/agent/                   # domain-researcher, spec-implementer
.opencode/skills/opendomain/       # SKILL.md
```

`AGENTS.md` is never overwritten, not even with `--force`: if you already keep your own, `od` does not claim it. The namespaced `.opencode/` files are written by `od` and are refreshed by `--force`.

```bash
od init --profile lean # start at Stage 3; the domain model exists elsewhere
od init --profile core # stages 0, 1, 3-8 (no opportunity discovery)
od init --profile full # everything (default)
od init --dry-run # report what would happen, write nothing
```

Other init flags: `--repository greenfield|brownfield|hybrid` and `--authority spec-first|spec-anchored|spec-as-source`.

## Working with `od`

`od` **reads and checks**; it does not author. You write the artifacts, `od` tells you whether they are consistent.

```bash
od status                        # where does the project actually stand?
od gate context                  # what is missing before the domain can start?
od gate --through domain         # run every gate up to the domain stage

od link --check                  # every referenced id must exist
od link REQ-012 derived-from EVD-014   # declare an edge (writes the TOML block)
od advance REQ-012 VALIDATED     # move along the lifecycle
od show REQ-012                  # one artifact's full record

od trace REQ-012                 # why does this exist?
od trace --forward REQ-012       # what implements and verifies it?
od impact RULE-007               # what breaks if this changes?
od graph --root REQ-012 --depth 3
od audit                         # traceability health across the workspace
od reference                     # the gates and the 37 artifact kinds
```

Change proposals follow the OpenSpec layout:

```bash
od propose tighten-reservation --summary "Tighten the reservation window"
od apply tighten-reservation
od archive tighten-reservation
```

### The nine gates

| Gate | Question it asks |
| ---- | ---------------- |
| `context` | Do we know what we are building, and what is already true? |
| `research` | Is the domain understood well enough to derive requirements? |
| `domain` | Is the domain model coherent, owned and cross-linked? |
| `requirements` | Is every requirement justified, testable and traced? |
| `opportunity` | Has anything been challenged, and is the chosen concept earned? |
| `specification` | Does the specification describe observable behaviour and nothing else? |
| `plan` | Is there a bounded, ordered plan that can realise the specification? |
| `implementation` | Did implementation satisfy the acceptance criteria without drift? |
| `completion` | Is the whole chain coherent, tested and free of critical unknowns? |

`od reference` prints this list as a rendered report; `od reference --json` returns it machine-readably, grouped by gate, with each rule's severity.

Findings carry one of two severities. `Blocking` fails the command — `od` exits non-zero — and means the phase cannot be considered complete. `Advisory` is reported and does not fail the command. The paper specifies three levels (`BLOCKER`, `WARNING`, `NOTE`); the implementation has two, and the paper's Section 11.7 records the six conditions whose severity disagrees with its own specification.

Gates are pure functions from the workspace to a report: they never mutate state, so running one twice gives the same answer, and a failure names the exact condition that broke.

### Scripts and CI

`--json` works on every command that reports. A failing gate exits non-zero, so `od gate --through specification` works as a CI step.

```bash
od gate --through specification --json > gate-report.json
```

`--no-color` and `-C <dir>` are available everywhere. `--strict` is accepted for explicitness and currently changes nothing: blocking findings always fail the command and advisory ones never do. `advisory_gates` in `opendomain.toml` and the `[schemas]` section are likewise written by `od init` but not read by the CLI today.

## Using it with opencode

This repository ships a working opencode integration. If you point opencode at a project that has an `opendomain/` workspace, the following become available automatically.

**Slash commands**

| Command | What it does |
| ------- | ------------ |
| `/od-status` | Where the project stands, and what is blocking |
| `/od-gate <gate>` | Runs a gate and reports the findings verbatim |
| `/od-trace <ID>` | Explains why an artifact exists, from its recorded links |
| `/od-impact <ID>` | What a change to an artifact would break |
| `/od-audit` | Traceability health before claiming work is done |
| `/od-record <topic>` | Writes a domain artifact, keeping its epistemic state honest |

**Subagents**

- `domain-researcher` — finds and records `SRC-`/`EVD-` artifacts. Its bash permission is `deny` by default with `od *` allowed, so it can check its own work but cannot run anything else.
- `spec-implementer` — one scoped task against an existing specification, gated before and after.

**Skill.** `.opencode/skills/opendomain/SKILL.md` loads on demand and carries the artifact format and the epistemic discipline. `AGENTS.md` holds the short version that is always in context, so the skill does not have to be.

To adopt this in your own project, run `od init` — it writes `AGENTS.md` and the nine `.opencode/` files for you — and put the `od` binary on `PATH`. It does **not** write `opencode.json`: the permission file below is this repository's own, and copying it is your decision.

```json
{
 "$schema": "https://opencode.ai/config.json",
 "permission": {
 "bash": {
 "od *": "allow",
 "od init *": "ask",
 "od link *": "ask",
 "od advance *": "ask",
 "od apply *": "ask",
 "od archive *": "ask"
 }
 }
}
```

`od *` is allowed and the five mutating subcommands are asked for, so reading the project is frictionless and changing it still needs consent. The `domain-researcher` subagent is stricter still: its own frontmatter denies all bash except `od *`, so it can check its work and can run nothing else.

> opencode reads its configuration at startup. After adding or changing `opencode.json`, agents, commands or skills, **restart opencode** or the new definitions will not be picked up.

## The artifact format

Each registry is a Markdown file of `##` headings, one per artifact. A fenced `toml` block carries the machine-checked fields; the prose below is for humans and is never parsed.

````markdown
## REQ-012 — Consult the movement history of an item

```toml
type = "FUNCTIONAL"
status = "DRAFT"
epistemic = "INFERRED"
confidence = "MEDIUM"
actor = ["ACT-002"]
derived-from = ["EVD-014"]
rules = ["RULE-007"]
```

**Statement**

The system SHALL allow authorized users to consult the chronological movements
of an item.
````

A malformed TOML block is reported with a line number, never guessed at. The prose is free-form, so you can write as much explanation as the subject deserves without risking a parse error.

Identifiers carry their kind as a prefix — `REQ`, `EVD`, `SRC`, `RULE`, `AC`, `SPEC` and 31 others (`od reference` lists them all) — optionally scoped, as in `REQ-INVENTORY-014` and `AC-INVENTORY-014-01`. Links are declared by the artifact that depends on the other, not the reverse: `REQ-004 derived-from RULE-001`.

## What gets enforced

The nine gates carry 58 named rules, each identified by a stable slug such as `gate-3/unjustified-requirement` so a failure can be cited rather than paraphrased. A representative selection:

| Rule | What it forbids |
| ---- | --------------- |
| `gate-3/unjustified-requirement` | A requirement with no `derived-from` an evidence record or business rule |
| `gate-1/orphan-evidence` | An evidence record not `derived-from` a source. An unsourced claim is not evidence |
| `gate-1/single-source` | Every evidence record citing the same single source — a claim repeated by one origin is not corroborated |
| `gate-8/assumption-reached-production` | A requirement whose `epistemic` is `ASSUMED`, `UNKNOWN` or `CONFLICTING` reaching the specification stage |
| `gate-5/how-not-what` | A specification that states mechanism rather than observable behaviour |
| `gate-4/unfalsifiable-hypothesis` | A hypothesis with no metric and no failure condition |
| `gate-4/feature-cloning` | A concept justified only by competitor parity |
| `gate-6/dependency-cycle` | Task dependencies forming a cycle |
| `gate-8/requirement-without-passing-test` | A requirement marked `IMPLEMENTED` with no verified test downstream |
| `gate-8/dangling-reference` | A link pointing at an identifier that does not exist |
| `gate-1/undeclared-epistemic` | An artifact that makes a claim but declares no epistemic state |
| `gate-7/epistemic-laundering` | An `ASSUMED` or `INFERRED` artifact marked `VALIDATED` or `VERIFIED`, with no intervening `EXPLICIT` evidence |

`od audit` reports traceability health across the whole workspace, including coverage ratios, unjustified artifacts, dangling links, and open conflicts.

## Recording how a claim got stronger

An artifact's `epistemic` state is a claim about the present. A `promotions` array records how it got there:

````markdown
```toml
status = "VALIDATED"
epistemic = "EXPLICIT"
promotions = [
 { from = "ASSUMED", to = "VALIDATED", evidence = ["EVD-014"], date = "2026-04-10" }
]
```
````

Without that record, a change from `ASSUMED` to `EXPLICIT` and a change of status are indistinguishable from each other — which is precisely the edit the framework exists to catch. `gate-7/epistemic-laundering` blocks a promotion from `ASSUMED` or `INFERRED` into `VALIDATED` or `VERIFIED` that cites no evidence, cites evidence that does not exist, or cites evidence that is not itself `EXPLICIT`. It also blocks on the current state alone: an artifact that is `ASSUMED` and `VALIDATED` at once has been laundered whether or not it wrote anything down.

A workspace that records no promotions at all gets an advisory, not a blocking finding. Absence of history is not evidence that laundering happened; it is evidence that laundering is currently undetectable, which is a smaller problem and a different one.
