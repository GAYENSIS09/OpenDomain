CLI reference

Five intents: locate, link, ask, share, evolve.

Locate — where do we stand?

opendomain status                 # project weather: real progress + blockers
opendomain gate context           # verdict of one specific gate
opendomain gate --through 3       # every gate up to requirements (--through takes 0-8)
opendomain audit                  # traceability health report
opendomain reference              # dictionary: gates + 37 record kinds

status every morning, gate before each stage, audit before saying "done".

Link — declare dependencies

opendomain link --check                         # does every link point to something real?
opendomain link REQ-012 derived-from EVD-014    # this requirement comes from this evidence
opendomain advance REQ-012 VALIDATED            # move a record to validated state
opendomain show REQ-012                         # full record of one artifact

Whoever depends always declares the link.

Ask — why, and what if it changes?

opendomain trace REQ-012                    # walk back to the source: the "why"
opendomain trace --forward REQ-012          # walk down: who implements and verifies it
opendomain impact RULE-007                  # what a change would invalidate
opendomain graph --root REQ-012 --depth 3   # the neighborhood, to see the web

Share — the whole base as one document

opendomain export                          # the whole base as one paginated PDF, Mermaid graph inside
opendomain export --format html            # the styled HTML the PDF is printed from
opendomain export --graph dot              # the traceability graph pre-rendered by Graphviz instead

A status cover (the same numbers status reports), the traceability graph, then every file in gate order with its records unfolded as readable tables. The PDF is printed headlessly by the machine's own browser (Edge/Chrome detected; --browser or OPENDOMAIN_BROWSER to pick another); without one, the styled HTML stays and the command says so. A printout is not evidence: cite the registries, rerun the export for a reader.

Evolve — change without rewriting history

opendomain propose tighter-reservation --summary "Tighten the reservation window"
opendomain apply tighter-reservation
opendomain archive tighter-reservation

Propose, apply, archive. Even refuted hypotheses are kept: a deleted failure gets re-derived, an archived failure teaches.

Write — registry plumbing

opendomain new REQ --scope inventory          # next free identifier (read-only)

Verify — the verification subsystem

Sections 9/10 of the paper, in the order F10 fixes: the rigour table, then the generated executable specifications, then the binding-provenance record, then the provisioner — each stage gated on the previous one.

opendomain rigour                 # the §9.7 table + which records declare a rigour
opendomain provision --dry-run    # stack detection + ordered selection (R1–R4), nothing written
opendomain provision              # .feature scaffolds with @AC tags + provenance — or a recorded refusal
opendomain bind                   # binding provenance (GENERATED/ANNOTATED/ATTRIBUTED/INFERRED) + depth
opendomain provenance             # each record's run citation verified against the archived run (F14/L9)

Nothing is ever installed and no generated file ever contains a passing assertion (PP4); the decision — or the §10.13 refusal, with its alternative mechanism — lands as a DEC artifact. bind reports findings; it is not a gate, so no legacy workspace starts failing.

Global options and CI

--json yields machine-readable reports on every reporting command, and a blocking gate fails the command — opendomain gate --through 5 --json > gate-report.json makes a CI step. --no-color and -C <dir> work everywhere.

Check the workshop itself

cargo test --workspace      # 167 unit tests + 2 doctests across the two crates (engine + cli)
cargo fmt --all -- --check

The workshop: crates/opendomain-core/ — the engine in one crate: model/ (artifacts, ids, vocabularies), registries/ (config, parser, workspace index), analysis/ (the nine gates, the traceability graph), scaffold/ (the single template writer), verification/ (Sections 9/10 + the F14 bridge) — and crates/opendomain-cli/, the thin opendomain binary that drives it.
