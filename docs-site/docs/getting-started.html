Getting started

Install the tool, create a project, get your first verdict.

Prerequisites

You need Rust 1.75 or newer. A single build is enough; afterwards the binary is self-contained.

1Install

The recommended way, with Rust installed:

cargo install --git https://github.com/GAYENSIS09/OpenDomain --locked opendomain-cli
opendomain --version

Prefer building from source? That works too — the binary lands at target/release/opendomain.exe (Windows) or target/release/opendomain (Unix):

git clone https://github.com/GAYENSIS09/OpenDomain
cd OpenDomain
cargo build --release

Put the binary on your PATH, or call it by its full path.

2Initialize a project

opendomain init doesn't create code — it prepares a tidy workbench and installs only: an opendomain/ folder of 42 files — 34 registries (one per artifact kind), 6 explanatory documents, opendomain.toml, and the tree's own .gitignore — plus an agent contract (AGENTS.md and the .opencode/ files: 15 commands, 3 role agents, 7 skills; the tree carries its own .gitignore too). 69 files in total. It records no project context; that comes next. Re-run, it reports what already exists without overwriting anything. Each generated tree (opendomain/, .opencode/) carries its own .gitignore — the project's own .gitignore is never touched; inside a git repo it advises the versioning split (the registries are the cited evidence — a project that versions a tree deletes that tree's .gitignore).

mkdir my-bookstore && cd my-bookstore
opendomain init --name my-bookstore
opendomain status
TipThree profiles cover common situations: full (everything, default), core (no innovation stage, for systems with an imposed scope), and lean (the domain model already lives elsewhere). --dry-run shows what would be created without writing anything. To take over an existing system, prefer --repository brownfield: current code is treated as a clue there, not a specification.

3Complete the context

An empty workbench knows nothing about your project yet. In opencode, run /opendomain-project: an agent reads the whole repository, researches the domain from the keywords it finds, fills in project.md, and asks you for whatever no reading could answer — jurisdiction, real users, constraints. Afterwards opendomain gate context should turn green. See With opencode for the full command map.

4Read your first verdict

At first, gates fail — that's their job: Blocking findings stop the command, Advisory findings are reported and recorded. opendomain status gives the project weather (what is ready, what is blocked), opendomain gate context returns the first gate's verdict with what's missing, and opendomain audit reports traceability health. Every refusal cites the exact rule: read it as an instruction, not a reproach.

Once two records are linked, try opendomain trace (why does this requirement exist?) and opendomain impact (what would need revisiting if this rule changed?). That's the moment the framework "clicks". Command details live in the CLI reference.

5Then the verification subsystem, when you're ready

The registries say what must be done; the verification subsystem (Sections 9/10) checks how the claims get stronger. opendomain rigour audits which requirement records declare a rigour, opendomain provision --dry-run detects the stack and shows the executable-specification scaffolds it would generate (nothing is installed), opendomain bind audits binding provenance and verification depth, and opendomain provenance verifies every run = "…" citation against the archive it names. Brownfield shows the adoption path that uses them step by step.
