Brownfield adoption

Take over an existing system without blocking its build — measure first, widen the spine capability by capability.

Existing code is evidence, not specification. The brownfield posture is the paper's Section 5.10: observed behaviour is classified before any change — documented, inferred, observed, legacy-accidental, intentional, compatibility-preserving, unknown — and nothing is deleted for being undocumented, nothing kept for being implemented. The walkthrough below is built only on commands that exist today; where a capability is still specified-only, it is marked spec-only. Bare commands are shipped: shipped.

1Survey — the tool reads the repo before you decide

shipped opendomain init detects existing implementation signals and tells you when a greenfield declaration would be the wrong posture; the recorded classification wins over flags unless you re-ran with --force. Use the brownfield profile up front:

opendomain init --repository brownfield --profile core
opendomain status

--profile core skips the opportunity stage (the domain will come from the code and its evidence, not from a brainstorm), which is Stage 3 onwards: domain, requirements, specification, plan, implementation, completion.

2Baseline — declare what is, honestly

shipped Create BAS-001 in requirements/baselines.md with the measured traceability coverage of the current state. The number is the deliverable (the paper says it explicitly: a project that learns its baseline is 20% knows what the work is). Record the measurement, not an ambition. The lifecycle runs forward: lowering a baseline is an edit, like going backwards through the registry.

opendomain new BAS
# BAS-001: coverage 20% of TEST-artifacted requirements, measured
opendomain status

3Inventory — classify, do not rewrite

shipped Pick one capability (one business flow). Register what the repo says:

opendomain new TERM   # glossary for that flow's terms
opendomain new ENT    # entities; owners declared
opendomain new RULE   # derived-from: the behaviour you can observe
opendomain new EVD    # evidence: repo behaviour as SRC ("repository" type)
opendomain reference  # the 37 kinds, labelled

Honesty rules apply unchanged: a rule you reconstructed from code is INFERRED until something documents it; a behaviour with no source at all is UNKNOWN. Epistemic laundering (repainting the inferred as explicit) is what gate 8 blocks — on brownfield it blocks copy-pasted confidence identical to how it blocks it on greenfield.

4One spine, end to end

shipped Close the chain for that one capability — requirement → specification → criteria → test — then run every gate up to completion:

opendomain link REQ-012 derived-from RULE-001
opendomain advance REQ-012 SUPPORTED      # after evidence copies it
opendomain propose one-capability-spec    # the work runs under changes/
opendomain gate --through 8

Gates are read-only pure functions: running them cannot break the build. In CI, capture the report rather than hard-failing while the baseline is low (--json gives the machine-readable result); move the gate to blocking per gate as its stage matures — that decision is yours, per pipeline stage.

5Growth — capability by capability, measured

shipped Repeat step 3–4 on the next capability, and update the baseline (BAS-002…). Drift discovered along the way (undocumented behaviour that turns out load-bearing) is filed in validation/drift.md, not fixed silently. Two mechanical checks keep the posture honest:

  • opendomain audit — coverage, orphan evidence, dangling links;
  • opendomain trace --provenance REQ-… — nearest-source-first: a requirement whose chain stops at a repository behaviour reads as what it is.

6When new work is agent-executed

shipped The increments themselves can run through the execution harness:

opendomain spec new 002-drift-migration
opendomain ground 002-drift-migration     # fingerprint of the brown tree
opendomain plan 002-drift-migration       # DAG; incomplete agents refused
opendomain run 002-drift-migration --executor mock   # first, offline
opendomain run 002-drift-migration --executor opencode

The grounding fingerprint matters most here: a brown tree drifts by design, and a run against a stale fingerprint fails before any model call — typed grounding_failure, upstream attribution, no spend. The F10/F14 machinery is now in the tool: opendomain provision generates the BDD scaffolds bound by @AC tags with provenance comments (offline, nothing installed), and run = "runs/run-NNN-…" is a first-class registry field — opendomain provenance verifies each citation against the archived run it names; a citation that names no archive is an appeal, not evidence.

Anti-patternAdopting on everything at once. The minimal-artifact principle is the cost bound: registries are a menu (per profile), and the 20%-baseline is a floor, not a ceiling you must jump to. If the domain is low-entropy (pure UI, no regulation), the framework's own prediction is that its overhead is unjustified — and it gives the falsification condition in the paper rather than hiding it.
NoteThe brownfield taxonomy and the baseline discipline are the paper's Section 5.10; reverse specification is called out in the limitations (L7) as the least-developed path. The framework does not promise the walk is free — only that every step is measured and that the measurement is the artifact.
