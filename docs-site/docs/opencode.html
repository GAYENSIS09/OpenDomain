With opencode

The same assistant, with a work contract.

Point opencode at a project containing an opendomain/ folder: it inherits commands, roles, and a discipline of evidence. You keep the AI's creativity; the framework imposes honesty on it — when it doesn't know, it writes UNKNOWN instead of inventing.

Reading commands

CommandRole
/opendomain-statusWhere the project stands, and what is blocking — in ten seconds.
/opendomain-gateRuns one gate and reports the verdict as is, without softening it.
/opendomain-traceTells a record's origin from its recorded links.
/opendomain-impactLists what a change would invalidate, before touching code.
/opendomain-auditFull health report before declaring "done".

One command per stage

CommandStageWhat it does
/opendomain-projectContextReads the repo, researches the domain, fills in the context, asks you the rest.
/opendomain-researchResearchFans out parallel research and merges corroborated evidence.
/opendomain-recordAnyWrites one record while staying epistemically honest.
/opendomain-domainDomainGrows the model by one bounded increment.
/opendomain-requirementsRequirementsDerives a small batch of justified, testable requirements.
/opendomain-opportunityOpportunityChallenges the design, earns one falsifiable concept.
/opendomain-specSpecificationSpecifies one capability as observable behaviour.
/opendomain-planPlanProduces one bounded, ordered plan with decisions.
/opendomain-implementImplementationRoutes through the verified harness — a TASK to the architect, a SPEC/AC through its TASK record.
/opendomain-completeCompletionReuses the audit, then calls the release: ship or stop.

Every command answers summary-first — verdict, top blockers, one next action — with the tool's full output in an appendix. No wall-of-gates noise.

Three roles

context-completer, the interviewer. Owns Phase 0 context: it reads the repository itself, delegates external research to the investigator, then asks you what no reading could answer. Brought in by /opendomain-project.

domain-researcher, the investigator. It reads, searches, and reports only dated sources and evidence, fanning out in parallel by keyword. Called by the interviewer, /opendomain-research, /opendomain-domain, and /opendomain-requirements. By default it can hardly execute anything — except opendomain * to check its own work.

opendomain-harnais, the harness architect. A TASK record becomes a verified agent system: plan (the record is the task description), grounding, kits, run under the gates, per-attribution recovery. Called by /opendomain-implement on a TASK-. Bash deny by default with opendomain * + read-only repo commands allowed; doctrine in the opendomain-harness skill. There is no direct-coding role: every agent-executed implementation goes through the verified harness.

opendomain-harnais, the harness architect. A fourth role — a bounded subagent, never a primary persona. It turns ONE TASK-### record into a verified agent system: opendomain plan TASK-012 (the record is the task description T), grounding, kits (opendomain build), then the run under the gates (opendomain run) — where the coordinator, not the architect, applies them — and per-attribution recovery. Its doctrine lives once, in the opendomain-harness skill; the role file carries identity, report shape, and stops. Called by /opendomain-implement TASK-….

The fourth role: the harness architect — not a persona

There is no primary persona, and the fourth role is a bounded subagent: opendomain-harnais, the harness architect. The harness is driven the way every other stage is: a command hands off to a role, a role loads a skill. /opendomain-implement names a TASK-### → the task record is the task description T: the architect compiles it into a DAG of agents (opendomain plan TASK-012), grounds, equips each one with a complete execution kit (opendomain build), then drives the run — where the coordinator, not the architect, applies the gates. The execution doctrine lives once, in the opendomain-harness skill — no per-platform copies, nothing to diverge. Doctrine: see The harness Brownfield.

The same projection mechanism is what the runtime agents themselves receive: each node of a run graph is written as its own agent file (universal deny, then one allow per whitelisted tool), so least privilege is enforced by the executor, not suggested by a phrase in a prompt.

Six skills

The framework's know-how, loaded on demand by commands and roles:

SkillLoad it when…
opendomainYou need the shared discipline and the map to the other five.
opendomain-epistemicsChoosing a knowledge value, recording a promotion, checking laundering.
opendomain-artifactsWriting or repairing any record — format, ids, relations.
opendomain-researchGathering evidence — parallel search, triangulation, saturation.
opendomain-gatesReading any gate, status, or audit output — identifier to action.
opendomain-harnessThe work executes through agents — the execution doctrine: task → DAG → kits → run under gates → attribution.
TipCommands are thin routers (user experience), roles call each other (interviewer → investigator → architect), skills carry the know-how. Run the command for the stage you're in; it loads the right skill and delegates to the right role. Implementation has ONE path: through the verified harness — spec-implementer was removed so agent-authored code can never bypass the run archive.
