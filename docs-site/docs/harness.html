The harness

When the work must be executed by agents — one door, gates everywhere, evidence archived.

The gates guard what a project claims. The harness is the framework's answer to the other half: work executed by agents. It turns one TASK-### record — the task description, living in the registries with its objective, constraints and acceptance criteria — into a verified agent system: planned, grounded, equipped, executed, archived. There is one door, /opendomain-harness, and no free-standing implementer beside it: the framework deliberately struck that role off. Anything agents execute enters the claims world through it — through the same nine gates, including implementation (gate 7), which still polices every "done" with cited evidence.

The flow, in six phases

The harness agent carries these as phases; the CLI commands do the writing:

PhaseCommandsWhat it produces
0 — Inventoryopendomain status, audit, doctor, opencode auth list, opencode mcp listGround truth before anything writes: what stands, what runs, what is missing — recorded as worded unknowns, never filled in.
1 — Needs are recordsopendomain new, spec new <slug>A task that cannot be traced to a record with acceptance criteria is refused: back to the caller, nothing invented.
2 — Ground & constructopendomain plan TASK-012, ground <slug>, build <slug>A DAG compiled from the record; a repository fingerprint that must replay before any model runs; every node equipped with a role, a tool whitelist and acceptance criteria, and every node-agent written to .opencode/agent/ — reviewable before the run.
3 — Verification loopopendomain validate, doctor, the bound gate commandsAfter every build, no exceptions: graph checks, executor checks, a live round-trip for every pinned model. Structural questions go back to the caller, never retried blind.
4 — Execution under gatesopendomain run <slug>Node-agents run in topological order; each gate check must replay before context propagates to the next node; retries carry typed feedback only.
5 — Attribution & archiveopendomain attribute, verify, resume, repatchEven a failed run ends in evidence, typed — local, upstream, structural — and archived as it ran.

What a run leaves behind

Each run archives append-only under opendomain/harness/runs/run-NNN-<slug>/ — the frozen graph, trace.jsonl (Start/Passed/Retry/Failed per node), context/ (every propagated gate check), and gates.log. opendomain verify <run> replays every gate on the archived outputs at any time, without an LLM; opendomain provenance verifies each record's citation run = "…" against the archive it names. A run without evidence is a run that did not happen.

Recovery follows the typed attribution, and costs what the fault costs:

AttributionMeaningRecovery
criteria_failure / spec_mismatch — localThe node wrote wrong code or ignored its contract.Fix the node; run <slug> --resume <run> keeps validated nodes frozen.
grounding_failure — upstreamThe world moved under a node: drift or stale grounding.Re-ground, then re-plan that node alone.
contract_violation — structuralThe decomposition itself is wrong.repatch <run>: a partial return to the plan; the revised node is re-admitted like any other.

The principles

Seven commitments carry the harness; they are the framework's face toward agent work:

No new runtime. Everything assembles from OpenCode primitives — agent files (mode, model, permissions frontmatter), skills and commands as the install-and-swap layer, MCP servers as the tool layer, ordered permissions as the sandbox — all reloading from disk on save.

Framed autonomy. Every agent recipe is deny-first and least-privilege (one allow per whitelisted tool), steps are bounded, and delegation depth ≤ 2 is enforced by omission: a parent admits children only through its own subagent permission, an allowlist of child ids. Least privilege is projected into the executor itself.

Models are pinned, not defaulted. The free tier is the default tier; the strongest authenticated coding model goes only where verified output is executed code. Every pin cites its tier and its reason, and one cheap round-trip proves the upstream alive before it carries real work. A refusing quota is a typed failure credited to the account — never re-tried at the identical shape.

Nothing propagates unverified. Before context moves between nodes, its gate replays: schema, patterns, tests — executed in the sandbox. This is the discipline of the nine gates, turned into the executor.

Every failure ends in evidence. Attempts replay only with typed feedback from the gate that failed them, and runs are archived exactly as they ran. No blind retries, no rewritten history.

Recovery costs what the fault costs. A local error never re-plans the whole system; a structural one never hand-edits a generated file — it re-enters the flow through repatch.

Self-improvement through the flow. Lessons land in an append-only memory as typed, dated rows; changes go through propose/apply; rollbacks are git plus a new row. The harness improves by recorded change, never by silent diff.

Where the authority on OpenCode lives

OpenCode evolves; the installed version decides. When opencode itself misbehaves — a permission that did not bite, an MCP server that will not start, a definition that did not reload — the authority is ordered: the installed binary first (opencode --help, --version, opencode mcp list, opencode auth list), then the doc index at opencode.ai/v2/llms.txt (agents, skills, commands, permissions, MCP servers, config, troubleshooting), then the opencode skill when a project installs it. The templates are the frame; the binary is the fact.

Using it

After opendomain init — the contract comes with the harness role, its command, and its skill — and one opencode restart, since it reads definitions at startup:

/opendomain-harness TASK-012

…returns the verdict first: PASS with the run directory, or the terminal failure typed and attributed; then up to three blockers with node identifiers, what was built, the archived run path and what should cite it, the run inventory, and the human-only gaps — disputed rules, missing acceptance criteria, scope calls: what no DAG can decide. The caller then records the TEST (or DRIFT) record citing the run, checks it with opendomain provenance, and moves the work with opendomain advance. No agent marks anything IMPLEMENTED or VERIFIED on its own.

StatusThe execution-plane commands (plan, ground, build, run, verify, attribute, repatch) are carried by the CLI distribution your install comes from — opendomain --help is authoritative about your install, and a command absent from it is a fact about the tool, not a suggestion to assume it. A build without the execution plane still carries the whole claims side — registries, gates, provenance — and keeps it coherent.
