The harness

Agents build the work; every output passes its gate before it propagates. Full execution doctrine.

Knowledge alone does not ship software. The second half of OpenDomain is the execution harness (opendomain/harness/): a task becomes a DAG of specialised agents, the coordinator runs them in topological order, and no output ever reaches downstream context before its acceptance gate passes — yi ∈ Ci. The registries enforce the same discipline at rest; the harness enforces it at runtime.

The harness follows Meta-Agent: From Task Descriptions to Verified Multi-Agent Systems (the paper is kept locally, not committed). Every agent carries a full specification σi — a natural-language role, a least-privilege tool whitelist, an explicit input/output contract, machine-checkable criteria. It is never admitted into the system until that spec is complete.

The canonical loop

Generate → Verify → Attribute → Refine. A rejected output is not simply retried: it returns as a typed failure (f ∈ F) with structured feedback — contract violation, criteria failure, grounding failure, sandbox violation — at a given attempt number, and each type carries its own recovery directive. The agent never self-gates: the coordinator verifies, the agent only produces.

Failure kindAttributionRecovery
SpecMismatch · CriteriaFailurelocalretry the same agent, ≤ max_attempts, with the gate's typed feedback
GroundingFailureupstreamre-run the grounding/dependency first — a stale foundation is not the agent's fault
ContractViolationstructuralthe decomposition itself is faulty — partial re-plan via opendomain repatch
SandboxViolationstructuralfix the configuration — the agent never ran; widening is an explicit --allow decision, never a retry

The cost of recovery follows the locality of the error: never a blind global retry, never a whole-system re-plan for a local slip.

The six pillars of an agent runtime

opendomain build does not emit vague prompts — every agent of a spec receives a complete kit, and the shared contract opendomain/harness/agents/<slug>/AGENTS.md renders all six pillars from the real graph:

  1. The agent loop. The coordinator (opendomain run) calls each agent in topological order with its upstream context, parses the response, applies the gate, and replays targeted attempts. The agent's job is one pure generation: return only the JSON object of its output contract. The runner executes the criteria commands itself — no agent ever "finishes" while its commands fail.
  2. Tools — least privilege. Each agent gets its whitelist in its σi and in its prompt; using a tool outside the list is a violation. Better: the whitelist is projected into the executor itself — OpenCode node-agents are written to .opencode/agent/<id>.md with V2 permissions, a universal deny first and one allow per whitelisted tool (last match wins), and Claude Code receives --allowedTools. The executor defaults to denial, so the whitelist is not a sentence — it is a property of the runtime.
  3. Context & memory. Context = the validated outputs (yj) of the upstream dependencies, injected bounded (~6 000 characters, never re-extended on demand). Memory = harness/memory/registre.md records past typed failures; consult it before improvising.
  4. Sandbox. Criteria commands run in the project's logical sandbox — a binary allowlist and a repository-bounded cwd from config.opendomain.toml [sandbox]. A binary off the list is refused before execution with a typed SandboxViolation. Honesty doctrine: this is a logical muret, not OS isolation — a container remains the only real wall, and the template starts closed.
  5. Hooks & controls. An automatic gate on every output (schema, patterns, test/lint commands), a cross-review by the verificateur node before propagation, and opendomain verify <run> that replays every gate on an archived run at any time.
  6. Skills & instructions. Reusable procedures live in the registry (opendomain skill add|new), are resolved per need, attached to the node prompts they apply to (applies-to), and injected bounded.

The lifecycle, milestone by milestone (M1–M7)

The harness was built as seven verified milestones; each is a command, and each carries its own guarantee:

#CommandWhat was proven
M1opendomain plan <slug>The spec T becomes a DAG of agents σi. Offline by default: a canonical deterministic decomposition (analyste → strategie → synthese → verificateur), specialised by the spec (language, constraints, named forbiddens). With --llm, OpenCode proposes the graph through the same Generate → Verify → Refine loop, ≤ 3 attempts — its proposal is never trusted. Admission requires complete contracts (role, tools whitelist, output schema, criteria Ci): an incomplete graph is never written. The archive (graph/<slug>.json) and the active graph (graph/graph.json) are both written.
M2opendomain run <slug>Execution under verification: topological order, gates yi ∈ Ci before any propagation, append-only archiving of the full run, and resumption that is verified — a resumed output re-passes its gate before re-entering the context (attempts: 0 marks a re-indexed node); a corrupted archive re-executes rather than being admitted. Repository drift is replayed from the grounding fingerprint before any LLM call, so a stale repo fails typed grounding_failure and costs nothing.
M3opendomain verify · opendomain attributeVerification is replayable offline — gates are re-run on the archived outputs, and the proof of the original run is never touched (verify.log is separate from gates.log). Attribution classifies terminal failures Local / Upstream / Structural with a directive, and records whether the node later passed a real gate (healed — so a fix is not re-planned twice).
M4(automatic — attribute, run)The memory of lessons. A typed failure leaves a permanent trace in memory/registre.md (date | spec | run | node | kind | message), deduplicated per (run, node, kind) — the goal is to never pay twice for the same error. Lessons feed back into prompts: the attribute → memory → re-plan arc is closed.
M5opendomain benchNot AI benchmarks to reproduce (HumanEval/MBPP…) but mechanical invariants of the harness itself, offline and deterministic: invalid graphs refused; gate intercepts any corruption (required, forbidden); retry with feedback converges; attribution is correct per failure kind; verified resumption does not re-execute; the sandbox is honoured before execution; the resolver admits one provider per need. A failed bench exits non-zero — usable in CI.
M6opendomain skill add|new · opendomain resolveModularity without redundancy. A registry of components (skills, tools, MCP servers, executors) declares what each provides and what it requires (bins, env, files). The spec declares needs; the resolver picks exactly one provider per need — preference preferred → local → remote (the principle of locality) — then checks every requirement against the machine. A need without provider is a typed miss, never a silent invention.
M7opendomain repatch <run>Partial re-planning, with a defined partiality. After a structural attribution, the canonical return is not a whole re-plan: a verified output is an asset. Frozen: id, depends_on, contract.input_schema (upstream edges — verified outputs stay anchored). Revised: role, tools, contract.output_schema, criteria. Never: criteria.schema_check (a gate cannot be disarmed by a re-plan) nor the gates' strict. Offline revision is admitted only when carried by evidence — every gate refusal for that node is a pure "required X missing", and X ∈ required; anything else routes to --llm, where the meta-agent's revision is itself verified (partiality + completeness, ≤ 3) before any write. Sandbox violations bypass node revision entirely: the harness stopped a command, not the agent.

The commands

CommandWhat it does
opendomain spec new <slug>Creates opendomain/harness/specs/<slug>/spec.md from the template — one folder per job, append-only.
opendomain workflow new <kind> <slug>Pre-fills a spec from a domain playbook: migration, refactor, tests, doc — a starting point, not doctrine: the planner stays master of the DAG and the harness of the gates.
opendomain ground <slug>Design-time grounding: project markers, manifests, README, toolchain into grounding/<slug>/repo-scan.md, dated and sourced — plus a fingerprint replayed before every run.
opendomain plan <slug> [--llm]Spec → DAG (M1). A TASK-### identifier resolves the registry record as the task description T — the harness triggers on the plan, not on a re-typed spec.
opendomain build <slug>Each agent's execution kit: shared AGENTS.md (six pillars), per-node σi (<id>.md), machine projection (<id>.kit.json), and a construction report — PASS/FAIL per agent. Incomplete → non-zero exit.
opendomain validate []Static rejection: unique ids, no self-loop, no dangling edge, no cycle — with the failing nodes named.
opendomain run <slug> [--executor opencode|claude|mock]M2. mock is deterministic and conformant to the canonical graph — CI, demos, and harness self-checks without an LLM.
opendomain verify <run>M3 replay.
opendomain attribute <run>M3 attribution + M4 memory.
opendomain repatch <run> [--llm] [--allow BIN]M7.
opendomain resolve <slug>M6 resolution, written to agents/<slug>/resolve.md.
opendomain skill add <url|path> / opendomain skill new <id>Install (curl for URLs) or start (template) a skill; the frontmatter is regenerated canonical (provides, applies-to).
opendomain doctorExecutor-agnosticism made verifiable: opencode, claude, aider, git, cargo, node, python — each [ok] or [absent], with the fallback doctrine spelled out (no LLM → deterministic mode still works: init/validate/gates offline).
opendomain benchM5 invariants.
opendomain rigourThe §9.7 rigour table, plus the workspace audit: which requirement/criterion records declare a rigour today, and which declarations match no row.
opendomain provision [--dry-run]F10 chain: repository-only stack detection, the ordered selection rules, then generated .feature scaffolds with @AC tags and provenance comments — or a refusal recorded as a DEC artifact. Nothing is installed.
opendomain bindBinding provenance (GENERATED/ANNOTATED/ATTRIBUTED/INFERRED) and verification depth (executed/discovered/declared). Findings, not gate rules.
opendomain provenanceThe F14/L9 bridge: each record's run = "…" citation verified against the archived run it names — and the runs no record claims.

Runs are evidence

Every run archives run--/ — append-only, insert-only, never rewritten after the fact:

runs/run-002-migration/
├── graph.json         # the frozen graph of THIS run
├── trace.jsonl        # events: Start, Command, Passed, Retry, Failed
├── context/           # the validated y_i, one JSON per agent
├── gates.log          # gate verdicts, one line per event, commands included
└── attribution.md     # typed failure + directive (on failure)

… and the lesson goes to opendomain/harness/memory/registre.md (append-only).
└── memory → registre.md # the lesson, if attributed

That folder is the basis for commits (context/ is the work state), rollbacks, and diffs between strategies — and for M2 resumption, which re-queues each archived output through its gate.

Executor-agnosticism

The executors are components, not identities: OpenCode, Claude Code, Aider, or a deterministic mock, all behind one trait. The runner always owns the gates — even a mock cannot produce an output that propagates without verification. opendomain doctor makes the contract verifiable instead of assumed; opendomain bench proves the mechanics without any LLM; and the offline planner keeps the whole pipeline usable with no network at all.

Configuration governs, it does not decorate

The workspace's single config — opendomain/opendomain.toml — is read by the CLI and handed to the runner; there is no second harness config to diverge from:

  • [gates] — strict = true (fail-closed: a green verdict is never advisory; the CLI refuses loudly a config that says otherwise) and max_attempts (the retry budget, proportional to locality).
  • [sandbox] — enabled + an allow list of binaries for criteria commands (template starts closed; opendomain repatch --allow records an explicit widening into the general config and the run log).

Both sections have defaults in the engine, so a workspace that omits them runs exactly as the paper prescribes.
