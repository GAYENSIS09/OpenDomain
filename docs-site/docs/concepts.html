Concepts

The three ideas everything else follows from.

Say how you know

"In Senegal, a standardized invoice must carry a NINEA" can be checked in the General Tax Code. "Invoices probably need an approval status" is a guess. Once copied into requirements, nothing distinguishes these two sentences anymore — and that is how clean-but-wrong software is born.

OpenDomain therefore requires every record to carry a knowledge label, with no default value:

StateMeaningExample
EXPLICITObserved in an authoritative source.The mandatory NINEA, Tax Code article.
TACITKnown through practice, never written down.The cashier eyeballs stock before validating.
HYBRIDOfficial source combined with experience, reasoning recorded.Delivery lead time: written rule + observed traffic.
INFERREDDeduced, to be confirmed, derivation recorded.Returns seem to spike on Mondays.
ASSUMEDTemporary position to move forward, with an expiry.Twenty concurrent users max, to revalidate.
UNKNOWNAcknowledged as unknown.Rate for digital services: not established.
CONFLICTINGTwo serious sources disagree.The accountant says "monthly", the text says "quarterly".
NoteTACIT is not inferior to EXPLICIT. The unwritten know-how of the people doing the work is often more decisive than the official procedure. The framework records both and flags their divergence instead of burying it.

Link everything to its evidence

The framework forbids promoting an outside statement directly into a requirement. The permitted path always goes through the same stations:

  1. Source — the page, the law, the interview, dated and recorded.
  2. Finding — what the source literally says.
  3. Interpretation — what that means in our situation.
  4. Candidate need — the problem this might answer.
  5. Requirement — the "the system SHALL…", only once the need is confirmed.

The classic example: a competitor writes "our software handles stock reservations", and the assistant infers "the system SHALL handle reservations". But the page says neither why, nor whether it is an obligation or a comfort, nor where reservation sits relative to payment. Until field evidence confirms the need, the requirement stays a visible hypothesis — the leap is blocked.

When this path is honored everywhere, all records form a single genealogy (source, evidence, business rule, requirement, specification, test). You can then walk back to the source (od trace) or list a change's downstream (od impact) as plain graph traversals.

Refuse whitewashing

The most ordinary cheating: assumed in January, forgotten in March, marked "validated" in June. OpenDomain calls this epistemic laundering. Moving from ASSUMED or INFERRED to "validated" without bringing genuinely EXPLICIT evidence is blocked by the gate-7/epistemic-laundering rule. Changing the label is not evidence.

To progress honestly, you keep a promotion journal — where from, where to, on which evidence, on what date:

```toml
status = "VALIDATED"
epistemic = "EXPLICIT"
promotions = [
  { from = "ASSUMED", to = "VALIDATED",
    evidence = ["EVD-014"], date = "2026-04-10" }
]
```

A project with no journal at all gets a mere warning: missing history doesn't prove cheating, but it makes cheating undetectable.

The rest of the picture

Three choices complete the frame. The opportunity stage frames innovation: formulate falsifiable, testable hypotheses instead of copying competitors — and "no opportunity" is an honorable conclusion. The rejection of MVP as a compass prefers vertical increments that are complete in evidence. Three-loop verification nests specification, behavior, and tests, with rigor chosen per requirement type rather than imposed globally. The spirit stays the same: first understand the world as it is, then improve it — proving each step.
